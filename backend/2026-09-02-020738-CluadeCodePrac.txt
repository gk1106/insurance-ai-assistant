     Insurance AI Assistant — Base Backend Architecture

     Context

     This is a learning project: an AI-powered Insurance Assistant. The eventual
     scope includes customer/policy/claim/renewal management plus a large AI
     surface (chatbot, tool calling, RAG, MCP, agents, subagents, orchestration)
     built with Spring AI + Claude. The project directory (backend/) is
     currently completely empty — no code exists yet.

     This design covers only the base backend: Customer management, Insurance
     Policies, Claims, Policy Renewal, and (per user decision) a minimal
     authentication/authorization layer. The goal is a clean, textbook-standard
     layered Spring Boot architecture that a beginner-to-intermediate developer
     can implement directly, and that the later AI features can attach to (via
     existing service interfaces) without any restructuring.

     This is a design document only — no code is written in this phase. It is
     the reference for implementing the base backend next.

     Stack: Java 17, Spring Boot 3, Maven, PostgreSQL, Flyway, MapStruct, Spring
     Security + JWT. (Spring AI/Claude come in a later phase.)

     Base package: com.insuranceai.backend

     3. Relationships Between Entities

     User (0..1) ── (1) Customer      [User.customer_id, nullable, unique]
     Customer (1) ──< (many) Policy
     Policy   (1) ──< (many) Claim
     Policy   (1) ──< (many) Renewal

     ┌──────────────┬───────────────────────┬───────────────┬───────┬─────────┐
     │ Relationship │      JPA Mapping      │  Owning Side  │ Fetch │ Cascade │
     ├──────────────┼───────────────────────┼───────────────┼───────┼─────────┤
     │ User →       │ @ManyToOne on User    │ User owns FK  │ LAZY  │ none    │
     │ Customer     │ (nullable)            │ customer_id   │       │         │
     ├──────────────┼───────────────────────┼───────────────┼───────┼─────────┤
     │ Customer →   │ @OneToMany(mappedBy)  │ Policy owns   │       │         │
     │ Policy       │ / @ManyToOne          │ FK            │ LAZY  │ none    │
     │              │                       │ customer_id   │       │         │
     ├──────────────┼───────────────────────┼───────────────┼───────┼─────────┤
     │ Policy →     │ @OneToMany(mappedBy)  │ Claim owns FK │ LAZY  │ none    │
     │ Claim        │ / @ManyToOne          │  policy_id    │       │         │
     ├──────────────┼───────────────────────┼───────────────┼───────┼─────────┤
     │ Policy →     │ @OneToMany(mappedBy)  │ Renewal owns  │ LAZY  │ none    │
     │ Renewal      │ / @ManyToOne          │ FK policy_id  │       │         │
     └──────────────┴───────────────────────┴───────────────┴───────┴─────────┘

     Rules:
     - All @ManyToOne sides use FetchType.LAZY (override JPA's EAGER default).
     - Prefer repository queries (findByCustomerId, findByPolicyId) over
       navigating lazy @OneToMany collections for listing/pagination — matches
       what future AI tool-calling methods will want.
     - No cascade REMOVE/ALL anywhere — claims/renewals/policies are never
       implicitly deleted with their parent. Use status flags (CANCELLED,
       disabled User) instead of hard deletes.
     - All FK columns nullable = false except users.customer_id.

     expiresAt

     Entity: Customer
     Request DTO fields: firstName, lastName, email, phoneNumber, dateOfBirth,
     addressLine, city, postalCode, country
     Response DTO fields: id, all request fields, createdAt, updatedAt
     ────────────────────────────────────────
     Entity: Policy
     Request DTO fields: customerId, policyType, coverageAmount, premiumAmount,
     startDate, endDate
     Response DTO fields: id, policyNumber, customerId, customerName,
     policyType,
     status, coverageAmount, premiumAmount, startDate, endDate, createdAt,
     updatedAt
     ────────────────────────────────────────
     Entity: Claim
     Request DTO fields: policyId, claimAmount, incidentDate, description
     Response DTO fields: id, claimNumber, policyId, policyNumber, claimAmount,

     * self-registration should force role=CUSTOMER; ADMIN/AGENT accounts are

     target = "customerName").

     6. Repositories

     All extend JpaRepository<Entity, UUID>, plus:

     - UserRepository: findByUsername, findByEmail, existsByUsername,
       existsByEmail
     - CustomerRepository: findByEmail, existsByEmail
     - PolicyRepository: findByPolicyNumber, existsByPolicyNumber,
       findByCustomerId(Pageable), findByStatus, findByEndDateBetween
       (expiring-soon queries)
     - ClaimRepository: findByClaimNumber, findByPolicyId(Pageable),

       (used for coverage-limit enforcement)
     - RenewalRepository: findByPolicyId(Pageable), findByStatus,
       findTopByPolicyIdOrderByRequestedAtDesc

     Use Page<>/Pageable on all list endpoints.

     7. Services

     Interfaces are the seam future ai.tools code calls directly — DTOs/plain
     types in, no web-layer types.

     - AuthService: register(RegisterRequestDto), login(LoginRequestDto) → 
       AuthResponseDto. Password hashed via PasswordEncoder (BCrypt); JWT issued
       via JwtService on successful login.
     - CustomerService: create/getById/getAll/update/delete. Rule: email
       uniqueness checked before insert; delete blocked (409) if the customer
       has policies.
     - PolicyService: create/getById/getByPolicyNumber/getAll/getByCustomer/upda
       te/cancel/getExpiringWithin(days). Rules: server-generates policyNumber;
       endDate > startDate; cancel sets status without deleting.
     - ClaimService: create/getById/getByPolicy/getAll/approve/reject/markPaid.
       Rules: claim only against ACTIVE policy; claimAmount ≤ coverageAmount;
       running sum of approved claims on a policy ≤ coverageAmount; status
       transitions constrained to SUBMITTED → UNDER_REVIEW → APPROVED/REJECTED →
       PAID, invalid transitions raise BusinessRuleViolationException.
     - RenewalService: create/getById/getByPolicy/confirm/reject. Rules: renewal
       allowed only if policy ACTIVE, or EXPIRED within a grace period (e.g. 30
       days); newEndDate > current endDate; confirm() updates the parent Policy
       (endDate, premiumAmount, reactivates status) via PolicyService, not by
       reaching into PolicyRepository directly.

     Validation split: Bean Validation (@NotNull, @Email, @Positive, etc.) on
     Request DTOs at the controller boundary via @Valid. Business rules
     (uniqueness, cross-entity checks, status transitions, grace periods) in the
     service layer, raised as ResourceNotFoundException (404) or
     BusinessRuleViolationException (400/409).

     Authorization rule for CUSTOMER-role users: service methods that list/fetch
     Policy/Claim/Renewal data should, when called by a CUSTOMER-role
     principal, filter to records owned by that user's linked customer. Simplest
     implementation for a learning project: check the authenticated principal's
     role/customerId in the controller (via @AuthenticationPrincipal /
     SecurityContext) and pass an ownership constraint into the service call, or
     enforce with @PreAuthorize expressions referencing the resource's customer
     id. ADMIN/AGENT bypass this filter.

     9. Security Design (Spring Security + JWT)

     - SecurityConfig: stateless (SessionCreationPolicy.STATELESS), CSRF
       disabled (pure REST API + JWT), PasswordEncoder bean (BCrypt),
       SecurityFilterChain permitting /api/auth/** and /swagger-ui/** publicly,
       everything else authenticated. Method-level @EnableMethodSecurity for
       @PreAuthorize on service/controller methods (role + ownership checks).
     - JwtService: issues signed JWTs (HS256, secret from config/env) containing
       sub (username), role, customerId (if linked), and expiry;
       validates/parses on each request.
     - JwtAuthenticationFilter: OncePerRequestFilter reading Authorization: 
       Bearer <token>, populating SecurityContext.
     - CustomUserDetailsService: loads User by username for authentication.
     - Passwords: BCrypt, never stored/returned in plaintext; passwordHash never
       appears in any Response DTO.
     - JWT secret and expiry externalized to application.yml / environment
       variables, not hardcoded — noted here because it matters even for a
       learning project (bad habit to hardcode secrets).

     ---

     10. Other Cross-Cutting Concerns

     - Global exception handling: single @ControllerAdvice
       (GlobalExceptionHandler) mapping MethodArgumentNotValidException → 400
       (field errors), ResourceNotFoundException → 404,
       BusinessRuleViolationException → 400/409, AccessDeniedException → 403,
       BadCredentialsException → 401, DataIntegrityViolationException → 409,
       fallback → 500.
     - Standard error shape (ApiError): timestamp, status, error, message, path,
       optional fieldErrors: [{field, message}]. This same shape is what a
       future AI tool-calling layer will parse to surface errors back to the
       LLM/user.
     - Validation: @Valid on all @RequestBody params.

     ---

     11. Database Choice: UUID Primary Keys

     Recommendation: UUID PKs (GenerationType.UUID, Hibernate 6 native, or
     Postgres gen_random_uuid() default via Flyway).

     - AI/tool-calling friendliness: UUIDs are safe to embed in LLM tool-call
       arguments without leaking sequential business-volume info (unlike
       id=1042), and since a future AI agent will pass entity ids as arguments
       it generates/echoes, opaque non-guessable identifiers are the safer
       default.
     - Human-readable business keys stay separate: policyNumber, claimNumber
       (e.g. POL-2026-000123) are what's shown to users/LLM in conversation; id
       (UUID) is the internal join key. Standard surrogate-PK + business-key
       pattern.
     - Minor tradeoff (larger index size, less insertion-order clustering) is a
       non-issue at this project's scale.

  1. Each stage

  Stage 1 — build (maven:3.9-eclipse-temurin-17)
  - Uses a full Maven + JDK 17 image, which is large but only exists temporarily
    during the build.
  - Copies pom.xml first and runs mvn dependency:go-offline before copying
    source. This means Docker's layer cache can reuse the
    downloaded-dependencies layer on rebuilds where only your Java files changed
    — pom.xml unchanged → that layer is skipped entirely.
  - Copies src/ and runs mvn clean package -DskipTests, producing
    target/backend-0.0.1-SNAPSHOT.jar. Tests are skipped here deliberately —
    this stage is for packaging, not verification; tests should run in CI before
    the image is even built.

  Stage 2 — runtime (eclipse-temurin:17-jre-alpine)
  - Uses a minimal Alpine-based JRE-only image (no compiler, no Maven, no build
    tools) — dramatically smaller than the build image.
  - Creates a dedicated non-root system user/group (spring:spring) — Alpine uses
    addgroup -S / adduser -S (BusyBox) rather than the useradd you'd see on
    Debian-based images.
  - Copies only the built JAR from the build stage via COPY --from=build, with
    --chown so the non-root user actually owns the file (a COPY without --chown
    would leave it root-owned and unreadable by the USER we switch to).
  - USER spring:spring switches off root before the container ever runs
    application code.
  - EXPOSE 8082 documents the port the app listens on — I matched this to
    server.port: 8082 in your current application.yml, not the framework's 8080
    default.
  - ENTRYPOINT runs the JAR directly with java -jar.

  2. Why multi-stage

  A single-stage build would leave the entire JDK, Maven, dependency cache, and
  source tree inside the final image — hundreds of MB of things that serve no
  purpose at runtime and only enlarge the attack surface. Multi-stage builds let
  the build stage do all the heavy lifting, then COPY --from=build pulls across
  only the one artifact that matters (the JAR) into a clean, minimal runtime
  image. Everything from stage 1 (Maven, JDK, ~/.m2 cache, src/) is discarded.

  3. How the final image runs the app

  At container start, ENTRYPOINT ["java", "-jar", "app.jar"] launches the Spring
  Boot fat JAR directly with the runtime stage's JRE 17 — no application
  server, no Maven involved at runtime. Configuration (DB URL, JWT secret, etc.)
  is expected to come from environment variables at docker run time, not baked
  into the image, which is why the Dockerfile itself never references any
  credentials.

  style it had before. That's fine for local dev, but worth reverting to env-var
  placeholders before this ever goes near a shared or production environment —

  CI vs. CD

  - CI (Continuous Integration) is what this workflow does: automatically build
    and test every change as it's proposed, so problems are caught immediately
    rather than discovered later. It answers "does this change work?" It
    produces no deployment — nothing leaves the CI runner.
  - CD (Continuous Delivery/Deployment) is the next stage: taking a change that
    passed CI and actually shipping it — pushing the Docker image to a registry,
    deploying it to a server/cluster, running database migrations against a
    real environment. Delivery means it's packaged and ready to deploy on
    approval; Deployment means it goes out automatically with no human gate.

  which point you'd need registry credentials as GitHub Actions secrets.

  How Maven caching works here

  cache: maven in actions/setup-java is a built-in convenience wrapper around
  actions/cache specifically tuned for Maven. Under the hood:

  1. It computes a cache key from a hash of all pom.xml files in the repo (it
     finds backend/pom.xml automatically regardless of working-directory).
  2. Before your build runs, it restores ~/.m2/repository (Maven's local
     dependency store) from a previous run's cache, if one matches that key.
  3. Your mvn test/mvn package steps then skip re-downloading any dependency
     already sitting in ~/.m2/repository — only new or changed dependencies get
     fetched from Maven Central.
  4. After the job finishes, it saves the (possibly updated) ~/.m2/repository
     back to the cache under that same key, for the next run to reuse.

  Because the key is derived from pom.xml's contents, adding/upgrading a
  dependency automatically invalidates the cache and forces a fresh download —
  you never get a stale cache silently hiding a dependency change. This is
  exactly what made your local mvn compile run fast the second time versus the
  ~65-second first run that had to download everything from Maven Central.

  How routing works

  App.jsx wraps everything in a single <BrowserRouter>/<Routes> tree:

  - /login is a standalone route — rendered outside AppLayout, so it has no
    sidebar/header.
  - The four content routes are nested inside a layout route (<Route 
    element={<AppLayout />}>). React Router renders AppLayout, and AppLayout's
    <Outlet /> is where the matched child (DashboardPage, etc.) actually appears
    — that's what gets you the sidebar+header shared across all four pages
    without repeating it in every page file.
  - / redirects to /dashboard via <Navigate replace />, and any unmatched path
    (*) also redirects to /dashboard — a minimal catch-all rather than a
    dedicated 404 page, to avoid an extra file for something not yet needed.
  - No auth guard exists yet on the dashboard/policies/claims/renewals routes —
    intentionally, since wiring auth was explicitly out of scope this round.

  Authentication flow

  1. User submits the login form → LoginPage calls useAuth().login(username, 
     password).
  2. AuthProvider.login calls authApi.login(...) → POST /api/auth/login via the
     shared apiClient.
  3. On success, the response { token, username, role, expiresAt } is written to
     localStorage and into React state → isAuthenticated flips to true.
  4. LoginPage explicitly navigates to /dashboard; independently,
     RedirectIfAuthenticated (wrapping /login) would also redirect away once
     isAuthenticated becomes true — belt and suspenders.
  5. On failure (401 invalid credentials, 400 validation, or a network error),
     the promise rejects, LoginPage's catch reads err.response?.data?.message
     (the backend's real message, e.g. "Invalid username or password") and
     displays it; a generic fallback covers network failures where there's no
     response at all.
  6. Logging out clears localStorage and state; RequireAuth then bounces any
     protected route back to /login.

  Where the JWT is stored

  localStorage, under a single key (insuranceai.auth), as JSON: { token, 
  username, role, expiresAt }. This is the "simple approach appropriate for a
  learning project" the api-integration skill calls for — it survives page
  refresh with zero extra machinery. The trade-off (also noted in that skill):
  localStorage is readable by any JS running on the page, so it's vulnerable to
  XSS in a way an httpOnly cookie wouldn't be. A cookie-based approach would
  require backend changes (which are off-limits here), so this is the correct
  choice given the constraint. getStoredSession() also self-expires: it checks
  expiresAt against Date.now() and clears anything already expired, so a stale
  token is never treated as a valid session.

  The axios interceptor

  Two interceptors on the single shared apiClient (src/api/client.js):
  - Request interceptor reads the stored session and, if a token exists, sets
    Authorization: Bearer <token> on every outgoing request — so no individual
    API call ever has to think about auth headers.
  - Response interceptor watches for 401 responses. On one, it clears the stored
    session and hard-redirects to /login (window.location.assign) — a full page
    reload rather than SPA navigation, which is a deliberate simplicity
    trade-off since an axios interceptor lives outside the React tree and
    doesn't have access to React Router's navigate(). It guards against
    redirect-looping by skipping the redirect if already on /login — that also
    means a failed login attempt (which itself returns 401) doesn't fight with
    the LoginPage's own error handling.

  Route protection

  - RequireAuth is a layout-route component: <Navigate to="/login" /> if not
    authenticated, otherwise <Outlet />. It wraps AppLayout in App.jsx, so
    /dashboard, /policies, /claims, /renewals are all covered by one guard
    rather than each page checking auth itself.
  - RedirectIfAuthenticated is the mirror image, wrapping /login — an
    already-authenticated user hitting /login is bounced to /dashboard instead
    of seeing the form again.
  - Both are pure client-side/UX guards. Per CLAUDE.md and the react-development
    skill, the backend remains the actual authority — every protected API call
    still requires a valid JWT validated server-side regardless of what the
    frontend router allows.

  How data flows into the dashboard

  DashboardPage fires four parallel requests on mount (Promise.all) through the
  api/* service modules — never axios directly.
  customerApi.list/policyApi.list/claimApi.list go through the shared apiClient,
  which attaches the JWT via its request interceptor. Results are combined into
  one state.data object:
  - Total Customers / Policies / Claims — straight from each response's
    totalElements (accurate regardless of page size).
  - Active Policies / Pending Claims — computed client-side by filtering the
    fetched content array (status === 'ACTIVE'; SUBMITTED/UNDER_REVIEW for
    "pending"), since the backend has no count-by-status endpoint. I fetch with
    size=200 to keep this accurate at a learning-project scale — documented with
    a comment since it's a non-obvious constraint.
  - Policies Approaching Renewal — the raw List<PolicyResponseDto> from
    /policies/expiring?days=30, rendered as a table with StatusBadge.

  Three states drive the UI: loading → Spinner, error → ErrorState (with retry),
  success → the stat grid + renewal table (or EmptyState if nothing's expiring)
  — matching the frontend-design skill's loading/error/empty requirement.

  Real backend bug I caught and fixed

  Testing against the live backend surfaced something I'd gotten wrong: this
  Spring Security setup (no AuthenticationEntryPoint configured) returns 403 for
  missing/invalid/expired auth, not the 401 I'd assumed. That status is
  identical to the "correctly authenticated, wrong role" case. My original
  interceptor only treated 401 as "session dead, force re-login" — meaning an
  actually-expired session would've shown the misleading "you don't have
  permission" message instead of "please log in again." Fixed: a 403 is now only
  treated as a dead session when there's no valid stored session left
  client-side (using the existing expiresAt self-check in authStorage.js);
  otherwise it's left as a legitimate role-based error for the page to display.
  This is exactly the kind of bug that only a real request against the running
  backend would catch — build/lint couldn't have found it.

    wherever plugin:github:github is defined) for a headers.Authorization entry.
  - Either update it with a fresh, valid GitHub token (with the right scopes for
    whatever the plugin needs — repo access, etc.), or remove that header
